A second Supadata key, used only when the first runs dry

Every transcript fetch and channel discovery goes through one SUPADATA_API_KEY. When its monthly credits are gone, indexing simply fails. This plan adds SUPADATA_API_KEY_2, a small key ring that rolls over on a quota 429 and stays rolled, and a health line so you can see which key is live.

What happens today

One key, read in one place

src/config.py:222 reads SUPERDATA_API_KEY or SUPADATA_API_KEY into Settings.superdata_api_key: str. Eight constructors pass it straight through (cli.py ×2, four evals, chat/setups.py, agents/transcript_agent.py).

Fetcher: 429 is just an error

src/transcripts/fetcher.py:69 raises TranscriptFetchError("… HTTP 429 …") on any 4xx. The ingestion queue records the video as failed and moves on — every remaining video in the batch fails the same way.

Discovery: retries the dead key

src/transcripts/discovery.py:131 sleeps 0.5 s / 1 s and retries a 429 twice. Right for a per-second rate limit; useless for an exhausted plan, which returns the same 429 for the rest of the month.

Supadata says which 429 it is

Both cases are HTTP 429 {"error":"limit-exceeded"}. The details string tells them apart: "Plan usage limit was exceeded." (quota) vs "Request rate limit on current plan was exceeded." (throttle). Source: docs.supadata.ai/errors/limit-exceeded.

Where you add the key

Keys never live in the repo. The app loads ~/.env (or whatever YT_AGENT_ENV_PATH points at) via load_settings(). Add one line next to the existing key:

# ~/.env  — the file load_settings() reads; never committed
SUPADATA_API_KEY=sd_live_…first_key…
SUPADATA_API_KEY_2=sd_live_…second_key…   # new: used only after _1 reports "Plan usage limit was exceeded"
# SUPADATA_API_KEY_3, _4 … are picked up the same way if you ever need them
DEEPSEEK_API_KEY=…

local ~/.env

The only place a real key goes. Both serve and every CLI command read it.

How a request fails over

Rules the ring enforces

Try the active key

Header x-api-key comes from ring.active_key. Success (200/202/206) returns as before — no behaviour change on the happy path.

Classify a 429 by its details

Body parsed once. "Plan usage limit" ⇒ quota. "rate limit" ⇒ throttle. Anything else, or an unparseable body, is treated as quota only after the throttle retries are spent — so an unexpected 429 still fails over rather than looping.

Quota ⇒ mark, advance, retry once

The key index goes into exhausted with a timestamp and the reason string; active moves to the next unexhausted key; the same request is re-sent. Logged once at WARNING: supadata key 1 exhausted (Plan usage limit was exceeded); using key 2.

Throttle ⇒ existing backoff, same key

Discovery's 0.5 s × n retry moves into the ring so the fetcher gets it too. A throttle never advances the ring — that would burn the second key's credits on a transient.

Async jobs stay pinned

fetcher._poll_job polls /transcript/{jobId} with the key that started the job — a job belongs to the org that created it. The ring returns (response, key_index) so the poll loop can pin it.

Every key exhausted ⇒ SupadataQuotaError

Subclass of TranscriptFetchError / DiscoveryError so existing except clauses still catch it, but with a message that names the keys: all 2 Supadata keys exhausted (key 1: Plan usage limit…, key 2: Plan usage limit…). The ingestion queue surfaces that text on the job, so the UI says "out of credits" instead of "HTTP 429".

Visible in /api/health

New field "supadata": {"keys": 2, "active": 2, "exhausted": [1]} (indexes, never key text). Demo mode reports {"keys": 0}.

Sharing state matters for serve: YT_AGENT_INGESTION_WORKERS=3 means three fetchers run at once. If each built its own ring, key 1 would be "discovered exhausted" three times. Risks and edges

coupling The details string

Supadata could reword "Plan usage limit was exceeded." Mitigation: the classifier only needs the substring "usage limit", and any 429 that survives the throttle retries is treated as quota anyway — worst case is one extra second of backoff before failover.

cost The failover probe

Each new process re-discovers key 1 is dead with one 429. Supadata doesn't charge credits for a rejected request, so that's a wasted round-trip, not money. Persisting exhaustion to disk is the alternative — see decision B.

cache Discovery cache

Unaffected: the discovery cache key is path + params, not the API key. A result fetched with key 2 is cached identically.

async Job started, key dies mid-poll

Only possible if key 1 exhausts on the exact video that went async. The poll then fails with quota text; the queue retries the video and key 2 starts a fresh job. Acceptable, and noted in the readme.

demo App Runner

No keys, no fetches. load_settings(require_keys=False) returns an empty list; the ring refuses to be constructed and health reports {"keys": 0}. Nothing on the demo path touches this.

compat SUPERDATA_API_KEY

The old spelling still works as key 1. Numbered keys use the correct spelling only — no SUPERDATA_API_KEY_2.
