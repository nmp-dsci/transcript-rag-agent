Ship Like a Studio (s20) → transcript·lab

The bones are studio-grade. The face is borrowed, the polish layer is missing, and the app says several things twice.

I loaded all six pages of the live app (dark, with a light spot-check), read theme.css and the view components, and scored everything against the 31 levers from s20 Parts 3–5 that apply to a working tool. The verdict: the token architecture, evidence density and focus/semantic-colour discipline are already better than most shipped workbenches — but the visual identity is GitHub's palette on a system font, exactly one CSS transition exists in 743 lines, four layout defects survive at desktop widths, and the same facts render twice in five different places.

The four real problems

  1. Borrowed identity. --accent:#2f81f7, --bg:#0e1116, --good:#3fb950 — GitHub's dark palette, near-verbatim, under a 'Segoe UI'-first font stack. The system is literally named Instrument in its own header comment and uses no instrument of its own.
  2. No premium layer. One transition in the whole stylesheet (theme.css:508, the tree caret). Every hover snaps. Two infinite keyframe animations run with no prefers-reduced-motion guard.
  3. Layout defects. Pipeline's header row overflows the viewport at 1615px; the composer's scope row clips below the fold on short windows (the body is overflow:hidden, so it is unreachable, not just hidden); System Design has zero page padding and colliding store labels.
  4. Redundant prose & stats. Answer metadata printed twice per bubble, corpus totals in four places, the self-graded warning twice on one page, ~400 words of standing methodology prose on the Scoreboard alone. The cut list below removes all of it without losing a fact.

What I am not going to re-litigate: the dual-theme token set with components that never branch on theme, the :focus-visible ring, the semantic good/warn/bad triad, the setup identity colours pinned across themes, and the evidence-first content. Those are s20's operating discipline already banked — theme.css:9–77 is a real design system.

Part four

Design-system upgrades — one file, app-wide

Four changes to theme.css that lift every page at once. U1 is the identity move; the rest are corrections. No component library, no build-step change, one webfont pair.

U1 · the big one

Give the Instrument system its instrument

The stylesheet's own first line names it the Instrument design system — and there is a real, free Google pair called Instrument Sans / Instrument Serif that no devtool uses. Adopt Instrument Sans (600/700) as the display face — brand, view titles, panel headings, landing h1 — with Instrument Serif italic reserved for the single decorated keyword. Body, tables, and every data surface stay on the system stack; mono stays exactly as is. Two subsetted woff2 files, roughly 40 KB, and the app stops looking like a GitHub fork the moment the title renders.

U2

The motion layer, in one token

Add --dur:200ms and --ease (a workbench wants snappier than s20's marketing 300ms), then put transition: background --dur, color --dur, border-color --dur on the six shared interactive classes — .nav button, .btn, .pill, .tab, .rentry, table row hovers. U3

A type + spacing scale

Collapse 13 ad-hoc font sizes into seven tokens (--t-2:10px … --t4:20px, plus the landing display clamp) and the paddings onto a 4/8 ladder. Mostly mechanical find-and-replace; the visible change is that near-misses (11px vs 11.5px vs 12px doing the same job in different panels) become the same size, and future pages stop inventing a 14th.

Files theme.cssRisk low, diff is wide Effort ~2 h incl. both-theme sweep

U4 · the palette question

De-GitHub the neutrals; keep the semantics

The full palette swap is tempting and wrong — good/warn/bad and the six pinned setup identity colours are load-bearing meaning. The surgical version: shift the neutral surfaces off GitHub's exact greys with a subtle cool-slate hue bias (#0e1116 → #0f1219-family, light theme warmed a step), and move the accent one notch off GitHub blue toward indigo (#2f81f7 → #4f74f0-family, both themes re-derived). Setup swatches, good/warn/bad and all dim/border steps stay. With U1 this is enough to read as its own product; without U1 it is barely visible — which is why the two ship together or not at all (D2).

Part six

What I am deliberately not taking from s20

s20 was written for marketing sites built by agents. Half of its levers would damage a workbench. Recording the rejections so they stay rejected.

✕A full palette rebrand. The setup identity colours (theme.css:222–231) are pinned across themes because they label which agent answered — history entries and committed screenshots depend on them. good/warn/bad likewise. U4 touches neutrals and accent only.
✕Marketing heroes on workbench pages. The landing is the conversion surface; Chat through System Design are tools. No page inside the app gets a hero, a tagline, or a reveal.
✕Animating data. No count-ups on scores, no bar-grow on eval metrics, no row reveals on tables. Numbers that move read as salesmanship in an app whose thesis is "RAG you can audit".
✕Reference-and-mold from an award site. This app's uniqueness is evidence density plus the Instrument face — not another studio's layout. The reference here is its own static-workbench ancestor.
✕A component library or CSS framework. 743 lines of hand-rolled tokens that two themes share without branching is the asset, not the debt.
✕Lowering density. The chunk trees, ranked columns and matrix tables are correctly dense for their users. The cut list removes repetition and lecture, never data.
✕s20 Parts 2, 5, 6 (pipeline, org design, prompt library) — process reference for how this plan was built, nothing to ship in the app.

Risks, honestly

  • U1/U4 change how the product reads. That is the point, and it is a taste call — both are isolated to Phase 2 and reversible in one commit.

  • U3's diff is wide. Mechanical, but it will touch most of theme.css — the both-theme screenshot sweep is the real reviewer there.
  • Tests encode current markup. The Phase 1 cuts will break selectors in a few suites; updating them is part of the phase, not collateral.
