Field Guides: articles the corpus writes, and the reader edits

A new workbench tab where a Claude Agent SDK pipeline reads transcript chunks in full, writes a long-form guide with per-claim references, and then revises it from your in-page commentary. Ship Like a Studio is the first entry; LLM-as-a-Judge and Production GenAI Systems are next.

01

Goal and current state

What exists

.lavish/s20_ship-like-a-studio.html is a hand-run artifact: 23 videos, 838 chunks read in full, six parallel extraction passes, a Sources appendix that maps each video to the line it contributed. Nothing in the repo reproduces it. The closest code analogue is the pack builder and deep-research loop under src/rag/, and the Agent SDK is already used with a subscription token in demo/generator.py.

What you asked for

A tab that showcases the coding agent writing in-depth guides from chunks, with references, usable by humans for learning and by AI agents as guides. You add commentary in the page, submit it, and the agent applies it. New guides can be started in-app or from the terminal, billed to your Claude subscription.

What this plan adds

A committed guides/ artifact directory, a src/guides/ module (writer, verifier, reviser, catalog), four API routes plus one job stream, a guides CLI, and a Field Guides tab with a sandboxed reader, comment rail and compose panel. Six vertical slices, V0 to V5, each shippable on its own.

Naming, decided. The tab is "Field Guides", the module is src/guides/, the artifact directory is guides/. Ship Like a Studio already calls itself "a field guide from the transcript corpus", and it fits the tab row: Chat · RAG Pipeline · Scoreboard · Experiments · Field Guides · System Design.
02

The shape of a guide

Every guide is one directory, committed to git like experts/<topic>/ and evals/runs/ are today. It holds three outputs from one run: the human page, the agent-readable guide, and the machine-checkable claims. Revisions add versions; they never overwrite.

# repo root
guides/
  index.json                         # catalog: slug, title, status, versions, source counts, cite-valid %
  guide.css                          # the shared editorial stylesheet, extracted from s20 (paper/ink/ultramarine, Instrument Serif + Geist)
  ship-like-a-studio/
    manifest.json                    # topic, video_ids, chunk_count, model, compiled_at, current_version, provenance
    guide.html                       # current version, human page (what the iframe renders)
    guide.md                         # current version, agent guide: frontmatter + same sections + citations as [video_id@chunk_index]
    claims.json                      # every <cite> in the page: claim text, video_id, chunk_id, verified bool
    evidence/                        # extraction pass outputs, one JSON per cluster (the "6 parallel passes")
    corpus/                          # exported chunks, one .md per video, gitignored (rebuildable from Chroma)
    comments.jsonl                   # reader commentary: id, anchor, quote, body, status, resolved_in_version
    versions/v1.html  v2.html ...    # immutable history; guide.html is a copy of the latest
    receipts/v2.json                 # per-comment outcome the reviser wrote: addressed / deferred / rejected + reason

Free HTML with a contract, not a rigid template

Ship Like a Studio is good because it is bespoke: its own sections, levers, kill-lists, prompts. Forcing every guide through one JSON schema would flatten that. So the agent writes HTML, but under three rules a Python verifier enforces before anything is published:

  • Citations are markup. Every sourced claim carries <cite data-video="…" data-chunk="…">. The verifier resolves each to a real chunk in Chroma and checks the quoted span (when present) occurs in that chunk. Invalid cites fail the run; the pass rate is stored in index.json and shown on the card.
  • Stylesheet is shared. The page links ../guide.css and may add scoped extras. That keeps guides visually one family, as the six views of the workbench are.
  • Sections are addressable. Every section and paragraph has a stable id (s2-p4), so comments anchor to ids and the reviser edits in place instead of regenerating the page.

The same run emits guide.md, the version an AI agent consumes. It is a faithful markdown rendering of the same sections with YAML frontmatter (title, topic, sources, compiled_at, version) and citations as [video_id@chunk]. Dropping it into a skills/ folder makes it a Claude Code skill with no extra work.

The writing pipeline

The pipeline reproduces how s20 was actually made: whole-video reads, parallel extraction, one composer, sources traced per claim. Retrieval is used only to pick the videos; once chosen, the agent reads every chunk of every chosen video, not a top-k.

The agent contract: stateless, corpus-only

Every write and every revision is a fresh query() with no session carried over. The agent's whole world is what is on disk in guides/<slug>/ plus one retrieval tool. It cannot remember a previous run, and it cannot reach the internet.

RuleHow it is enforced
StatelessNo resume / continue_conversation; no session ids stored. All state the next run needs is a file: guide.html, claims.json, evidence/, comments.jsonl, corpus/. A run that dies leaves those files; the next run simply starts over from them. The runner passes the same prompt shape every time, so a revision is reproducible from the repo alone.
Corpus-only evidenceallowed_tools is exactly Read, Write, Edit, Glob, Grep scoped to cwd=guides/<slug>, plus one in-process MCP tool retrieve_chunks. WebSearch, WebFetch and Bash are not in the list, and disallowed_tools names them too, so the SDK refuses them even if the model asks. The system prompt states the rule in one line: evidence comes from the exported corpus and the retrieval tool only; if the corpus does not support a claim, say so rather than fill the gap.
The retrieval toolretrieve_chunks(question, video_ids?, top_k=10) is registered with create_sdk_mcp_server in src/guides/tools.py and wraps the same hybrid retriever the Chat tab uses (MultiTranscriptRagContextProvider.get_context, semantic + BM25 fusion, reranked). It returns chunk id, video, timestamp and text, so anything it surfaces is citeable as-is. Default scope is the guide's own video set; the whole corpus is one flag away when a comment asks for evidence the guide's videos do not hold.
Web only on requestA per-run --allow-web flag (CLI) or checkbox (UI) adds WebSearch/WebFetch to the tool list and stamps web_allowed: true plus every fetched URL into the manifest and receipt. Off by default; web-sourced claims must carry an <a> reference, never a <cite>, so corpus citations stay pure.
Tool use is loggedEvery tool call (file reads, retrieval queries, and the questions they asked) streams as a stage event and is stored in runs/<timestamp>.jsonl next to the receipt, so "how did the agent decide this" is answerable after the fact.

Revision is the same pipeline from stage 4

Open comments are a tracked batch. A fresh reviser session gets the current page, claims.json, the evidence files, and the comments with their anchors. It must edit in place, may re-read corpus/ or call retrieve_chunks for new evidence, and must return a receipt giving every comment id exactly one outcome: addressed (with the section id changed), deferred (reason), or rejected (reason, typically "the corpus does not cover this"). Verify runs again; publish bumps the version and marks comments resolved-in-vN. Missing ids in the receipt fail the job, which is the same rule the Lavish input playbook applies to its own tracked batches.

07

Risks and how the plan handles them

agent Fabricated citations

The verifier is a hard gate, not a score: a guide with an unresolvable cite does not publish. Extractors must copy verbatim quotes with chunk ids, and the composer may only cite claims that exist in evidence/. Pass rate is shown on the card so the portfolio claim is auditable.

agent Agent reaching outside the corpus

Tool allowlist plus explicit disallow of web and shell tools, cwd-scoped file access, and a system prompt that tells the agent to report gaps instead of filling them. Web access is opt-in per run and audited in the manifest. Sessions are stateless, so nothing from a previous run can leak into a new one unnoticed; every input is a committed file.

agent Untrusted HTML in the app

The page is agent-written. It renders in a sandboxed iframe with scripts allowed but no same-origin, and the verifier rejects external script tags and inline event handlers. The parent trusts only structured postMessage payloads.

ops Long jobs inside the server process

A write is 10–25 minutes and a few hundred thousand input tokens across subagents. The runner is one-at-a-time with stage checkpoints on disk, so a restart loses at most one stage. Subscription rate limits surface as a job error with the SDK message, not a hang; the runner gets a per-stage timeout.

ops SDK and binary on the host

The SDK spawns the claude CLI. It is an optional dependency group; the server degrades to read-only with a 503 hint. The demo container is unaffected by construction.

design Guides drifting apart visually

Shared guide.css plus the skill file's structure rules keep them one family while leaving section design free. Import of s20 proves the stylesheet against the reference guide first.

design Revisions that rewrite instead of edit

Stable ids, in-place edit instructions, and a diff summary in the receipt (which section ids changed). The version switcher lets you compare, and a revision that touches sections no comment anchored to is flagged in the receipt.

scope Corpus coverage for the two new topics

17 judge videos and 15 production videos are already indexed. That is the same scale as s20, so no ingestion is needed before V1 and V2. A guide's manifest records held-out or excluded videos with a reason, mirroring experts/packs.json.

scope Repo size

Each guide commits html, md, claims, evidence and versions: roughly 200–400 KB per guide. Exported chunk corpora are not committed; they rebuild from Chroma.
