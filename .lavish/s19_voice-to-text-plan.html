Voice-to-text in the chat composer

Press a mic button, talk, and watch the question appear as live text in the question box — then edit and send as usual. This plan compares Deepgram (key already in hand) against self-hosting STT inside this app, scores both on a production-grade rubric, and lays out the implementation.

Recommendation — Deepgram Nova-3 streaming, relayed through a FastAPI WebSocket

Use Deepgram's live WebSocket API (wss://api.deepgram.com/v1/listen) with interim_results=true, proxied through a new /ws/stt endpoint so the API key never reaches the browser. It scores 4.6 / 5 on the rubric vs 2.6 / 5 for self-hosting: sub-300 ms word-by-word streaming with zero model ops, for ~$0.46/hour of audio — and your $200 free credit covers ≈430 hours, effectively free at portfolio scale. Self-hosting inside this app is ruled out mainly by physics: the demo runs on App Runner at 0.5 vCPU / 1 GB, and Whisper-family streaming needs VAD + sliding-window re-decoding that competes with the CPU-pinned embedding stack locally.

The options

A · Deepgram Nova-3 streaming recommended

Managed live WebSocket API. You already hold the key.

  • True streaming: interim results word-by-word, typically <300 ms; is_final + speech_final mark commit points; smart formatting and punctuation built in.
  • Cost: $0.0077/min streaming (~$0.46/hr); $200 sign-up credit ≈ 430 hrs. A 15-second question costs ~$0.002.
  • Ops: zero — no model in the container, works on the 1 GB demo instance (mic hidden there anyway).
  • Costs you accept: audio leaves the machine; vendor dependency; needs network.

Wiring A1 (recommended): FastAPI WS relay — key server-side, demo gating consistent, ~200 LOC. A2 (later, optional): Deepgram short-lived token grant (~30 s TTL) lets the browser connect direct, removing relay hop and server bandwidth. The two are compared in depth in the next section.

B · Self-hosted STT inside this app not now

Run the model in-process or as a sidecar.

  • Whisper doesn't stream natively. Real-time means VAD + sliding-window re-decode (LocalAgreement) — 1–2 s text lag, silence-hallucination risk, and it's yours to maintain. faster-whisper (CTranslate2, int8) is the strongest CPU option but small/base is what fits real-time on CPU — a real accuracy step down.
  • Vosk streams partials natively and is light, but accuracy is clearly below Whisper/Deepgram — wrong trade for a portfolio piece.
  • Parakeet TDT v3 beats whisper-large-v3 on WER (6.3% vs 7.4%) and is extremely fast — but NeMo/ONNX integration + a DIY browser-mic streaming pipeline; realistically a GPU sidecar service, i.e. no longer "inside this app".
  • Hard blocker: App Runner demo = 0.5 vCPU / 1 GB; locally the embedding stack is already pinned to CPU (the MPS wedge) — an STT model competes for the same cores.
  • What it buys: audio never leaves the box, $0 marginal, offline, no lock-in.

When to revisit: if privacy/offline becomes a requirement — then as a separate sidecar behind the same /ws/stt contract, so the frontend never changes.

C · Browser Web Speech API baseline, not production

Free, zero-backend, streams interims — worth knowing why it's rejected: Chrome routes audio to Google's recognizer (no control, no SLA), Firefox doesn't support it, Safari support is inconsistent, and you can't pick a model. Fine as a hack-day fallback; it would undercut the production-grade story this feature is meant to tell.

Deepgram wiring in depth — A1 relay vs A2 direct, and the long-term answer

A1 · Server WebSocket relay best long-term for this app

Browser → /ws/stt → Deepgram. One extra hop, everything under your roof.

  • How it works: the browser opens one WS to your own origin; the endpoint opens a second WS to Deepgram with the key from config, then pumps audio up and transcript JSON down between them.
  • The strategic property — vendor abstraction: the frontend codes against your contract ({text, is_final, speech_final}), not Deepgram's protocol. Swapping Nova-3 for another provider, or a self-hosted sidecar in a privacy-first future, is a backend-only change. A2 bakes Deepgram's wire protocol into the React app.
  • Control lives in one place: session caps, per-IP rate limits, usage logging, and the demo-mode check all sit in the endpoint — enforceable, testable, and visible in your own logs rather than only in Deepgram's console.
  • Testing: the whole path is testable offline — Starlette's WS test client against a fake Deepgram socket. A2's browser→Deepgram leg can only be integration-tested against the real service.
  • What it costs: every audio byte transits your server (~4 KB/s per speaker on Opus — trivial at this scale) and each active mic holds two WS connections open. Adds ~10–50 ms on top of Deepgram's ~200–300 ms. Real pressure only arrives at hundreds of concurrent speakers.

A2 · Ephemeral token, browser → Deepgram direct scale/latency optimization

Browser asks POST /api/stt/token for a ~30 s scoped JWT, then opens the WS straight to Deepgram.

  • How it works: the server exchanges the master key for a short-lived, scoped token per session; the master key still never reaches the browser. The token TTL only gates connection establishment — the stream continues past expiry.
  • What it buys: the lowest possible latency (no relay hop) and zero streaming load on your server — Deepgram absorbs all concurrency. Your infra does one cheap POST per utterance session. This is the shape voice-agent products use at scale.
  • What it costs: two moving auth parts (token mint + refresh edge cases); the browser now talks to a third-party origin — CSP connect-src changes, and strict corporate networks sometimes block it; per-session caps and usage attribution move to Deepgram's console/webhooks instead of your own logs; and the frontend becomes Deepgram-protocol-aware, so a future provider swap touches UI code.
  • Migration cost from A1 is small: keep the same message shape, add the token endpoint, point the hook at Deepgram — the A1 relay can even stay as a fallback. Nothing about starting with A1 forecloses A2.

Long-term verdict

A1 is not just the easy first step — it is the better long-term architecture for this product. Its decisive property is that the vendor stays behind your own /ws/stt contract: cost controls, observability, and demo gating live in your codebase, the whole path runs in CI, and Deepgram is swappable (managed → cheaper provider → self-hosted sidecar) without touching the frontend. Its only real weaknesses — one extra network hop and relay bandwidth — are measured in tens of milliseconds and kilobytes per second, which this app will not feel until hundreds of people are speaking simultaneously. A2 is the right move when and if that scale or a hard latency budget arrives, and A1's message contract is deliberately designed so that migration is additive, not a rewrite. Build A1; keep A2 in the drawer.

Implementation plan (Deepgram · A1 relay)

1
Config — src/config.py: read DEEPGRAM_API_KEY from ~/.env; add YT_AGENT_STT_ENABLED (default on when a key exists) and YT_AGENT_STT_MODEL (default nova-3). Follows the existing YT_AGENT_* pattern exactly.
2
Backend relay — new src/api/stt.py with @app.websocket("/ws/stt"): reject when demo_mode or no key (the HTTP demo-gate middleware does not cover WebSockets — this check must live in the endpoint); open Deepgram WS with interim_results=true&smart_format=true&endpointing=300; two async tasks relay audio bytes up and {text, is_final, speech_final} JSON down; send Deepgram KeepAlive during pauses (it closes after ~10 s of silence otherwise); hard session cap (~120 s) and idle close for cost control. Promote websockets to an explicit dependency.
3
Health flag — add "stt": true|false to /api/health; the frontend renders the mic only when set (same pattern as the demo chrome), so demo mode and keyless dev degrade to today's UI.
4
Frontend hook — new frontend/src/chat/useSpeechToText.ts: getUserMedia → MediaRecorder (audio/webm;codecs=opus, 250 ms timeslice) → WS to /ws/stt; exposes {state, start, stop, committed, interim, error}; assembles finals and replaces the interim tail on each message.
5
Composer wiring — mic button beside Send in Composer.tsx; while recording, the textarea shows committed + interim (mic-owned, edits resume after stop); stop on button, on speech_final quiet, or on unmount; disabled while busy.
6
Tests — vitest: hook tests with mocked MediaRecorder/WebSocket (interim replacement, final commit, error path); pytest: relay test via Starlette's WS test client with a monkeypatched fake Deepgram socket; demo-mode rejection test.
7
Docs — readme: env vars, run instructions, and the demo-mode behavior note.

Risks & open questions

Risks

  • Safari Safari's MediaRecorder produces audio/mp4 (AAC), not WebM/Opus. Phase 2: an AudioWorklet → PCM linear16 path (encoding=linear16&sample_rate=16000) makes capture browser-independent. Phase 1 is Chrome/Edge/Firefox.
  • Idle cost An open mic left running bills by the minute. Mitigations in the plan: endpointing auto-stop, 120 s hard cap, close on unmount/blur.
  • First WS This adds the app's first WebSocket route — anything fronting uvicorn later (ALB, nginx) must pass upgrade headers. App Runner is unaffected (demo has no mic).

Open questions

  • Chrome-first ship (MediaRecorder only), or build the AudioWorklet/PCM path from day one for universal browser support?
  • English-only ($0.0077/min) or multilingual ($0.0092/min, language=multi)? Corpus is English-language YouTube — English-only seems right.
  • Any interest in the A2 ephemeral-token path now, or file it as a latency optimization once the relay works?
