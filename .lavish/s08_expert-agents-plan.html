Distilled expert agents

A plan for turning clusters of transcripts into standing experts — persistent, citable knowledge distilled offline from communal chunks — so a matching question is answered from compiled expertise instead of a fresh retrieval pass every time. Grounded in what already exists in transcript-rag-agent: the community-summarization machinery from GraphRAG, the multi-transcript retrieval scoping, and the ablation/matrix eval harness that already knows how to compare RAG variants head to head.

Current state — what already exists to build on

Nothing here is theoretical. Four pieces of existing infrastructure are 80% of an expert pipeline already, they just aren't wired together as one:

Corpus already clusters by domain

26 videos across 17 channels split cleanly into three domains the golden set already labels — property, ai-coding, career — because that's how the videos were actually sourced. The career domain (resume, LinkedIn, interviews — 8 channels, 6+ videos) is exactly the "resume expert" example.

Community distillation already ships (GraphRAG P4)

src/rag/communities.py already does cluster → LLM-summarize → store: Leiden over the entity graph, one summary per community, built up front so global questions read pre-built summaries instead of paying per query. Every claim it summarizes from carries chunk_id/video_id/upload_date provenance (GraphClaim) — the citation discipline an expert's knowledge card needs is already the house style, not a new invention.

Scoped retrieval already exists

MultiTranscriptRagContextProvider already narrows retrieval to a channel via channel_id, and the per-video summary store (src/rag/summaries.py) already picks relevant videos by embedding similarity. A "retrieval-only expert" — corpus scoped to one domain's channels — needs zero new indexing code, only a cluster→channel mapping.

The eval harness already compares variants

eval-ablation / eval-matrix already sweep named configurations over the same golden questions and report IR metrics, RAGAS scores, latency and token cost side by side — exactly "test different variants," just not yet crossed with an expert scope axis. Extending the cache-key/config-snapshot logic in src/evals/matrix_cache.py is the whole plumbing change.

What's genuinely new: (1) a job that turns a cluster's chunks into a standing, versioned expert profile — not just a summary but something an answer call reads instead of retrieving live; (2) a router that picks an expert for a question instead of the user picking a setup; (3) an eval axis that asks "does the distilled expert answer as well as live RAG, cheaper, and does it get better as the cluster grows."

The offline job runs on a schedule or on demand (mirrors index-graph / index-contextual today). The live path adds exactly one branch to POST /api/ask — the same shape as the document-review URL-detect branch already shipped (src/documents/detect.py → resolve.py): detect a signal, short-circuit into a different answer path, fall through to normal behavior otherwise.

Scoping note — "learning" here means curated re-compilation, not model training. This stack calls DeepSeek over an API; there's no path to fine-tune weights. "Improves over time" has to mean: the distilled knowledge card gets re-synthesized as its source cluster grows (more videos → a richer, re-run distillation pass), and — as a later phase — judged Q&A history feeds back into what the next distillation pass emphasizes. It's in-context knowledge curation, and the plan should never imply otherwise to a reader.

The build pipeline, stage by stage

1

Cluster — assign chunks to experts

Three methods, increasing in cost and decreasing in how much they need labelled data. All three are testable against each other using the existing golden-set domains as ground truth for "did this clustering recover the grouping a human would draw."

methodhowneedsfit here
Domain heuristic Reuse the golden set's existing domain field, mapped to channel_id. One expert per domain. Nothing new — the mapping already exists implicitly in the corpus. MVP Free, immediately testable, and matches the "resume expert" example exactly.
Embedding clustering K-means or HDBSCAN over per-video summary embeddings (already computed and stored in TranscriptSummaryStore). A cluster count or density parameter; no LLM calls. Discovers experts the heuristic wouldn't think to draw (e.g. a "negotiation" expert that spans career and property channels). Good ablation partner to the heuristic.
Graph community reuse Read index-graph's already-computed Leiden communities and roll them up to video/channel level. Requires index-graph to have run; entity-level, may be finer-grained than a useful "expert." Cheapest to try (zero new compute) but communities are topic-clusters within a domain, not across it — needs a rollup rule, not a 1:1 mapping.
2

Distill — synthesize a cluster into a knowledge card

The knowledge card is the artifact this whole feature is actually about — the thing that lets an expert answer without a live retrieval pass. It has to satisfy one hard constraint the rest of this stack already lives by: every claim traces to a source chunk. A card that can't cite back to chunk_id/video_id is a hallucination risk dressed up as an artifact, not a distillation.

Proposed schema — ExpertKnowledgeCard

Built the same way as community summaries: an LLM call per expert (not per chunk) over the cluster's top claims/chunks, capped and de-duplicated the way claims_per_summary already caps community summarization. Cached by a hash of the cluster's chunk-id set, so an unchanged cluster costs nothing to re-run — the same rule graph_extract.py and matrix_cache.py both already follow.

Recency-weighted salience

A claim's importance to the card isn't fixed at extraction time — it decays. Your own example is the clearest case: a property-tax rule change is the single most important thing the expert can say the month it airs, and unremarkable background context a year later, once every property channel has covered it and the market has priced it in. A claim about interview-answer structure, by contrast, barely decays at all. One decay rate for every claim would either bury the urgent update or keep a stale one prominent indefinitely — both wrong.

This isn't new machinery to invent: every claim already carries upload_date provenance (the same field the temporal GraphRAG route already reads to build a dated claim timeline), so recency weighting is that same "date-as-signal" idea moved from the answer side to the distillation-ranking side. Concretely, claim selection for a card becomes a function of topical salience (today's rule: co-mention count within the cluster) and a recency decay term — with the decay half-life set per claim category, not per expert: a "rule/rate/policy" claim decays fast (weeks-to-months), a "principle/how-to" claim decays slowly or not at all. The category label is a cheap addition to the existing extraction prompt, not a new pipeline stage.

claim categoryexampledecay behavior
rule_or_rate"CGT discount changes from July 2027"fast decay — high salience near upload_date, fades toward background once superseded or ~12 months out, whichever is sooner
principle"lead your resume bullet with the outcome, not the task"slow/no decay — recency contributes little; topical salience alone decides inclusion
market_observation"listings in this suburb are moving fast right now"fast decay, similar to rule_or_rate

A superseded rule doesn't just fade quietly — a claim whose decay has pushed it out of the card is a candidate for an explicit correction entry ("as of <date>, this changed from X to Y") when a newer claim on the same entity contradicts it, so the card can say a rule changed instead of just forgetting the old one ever existed.

3

Store — the expert profile

A new expert_profiles collection (metadata store, not vector search) holding the card above per expert, plus a new expert_knowledge Chroma collection embedding the card's playbook_sections so a large card can still be retrieved from selectively — the same "whole thing if it fits, ranked selection if it doesn't" rule src/documents/review.py already implements for reviewed documents. Reused directly, not reinvented.

Visualizing one expert — a bounded two-tier star, not a raw chunk fan-out

An expert's provenance is exactly graphable — expert at the center, edges out to what built it — but a direct expert→chunk star with hundreds of spokes (a career expert alone draws on 100+ chunks) would render as an unreadable hairball at any node size. The card's own structure already gives the graph its middle tier for free: expert → playbook_sections/principles → source_chunk_ids. Bounded fan-out at each level — an expert has a handful of sections, each section cites a handful of chunks — collapsed by default and expanded on click, the same disclosure pattern src/documents/review.py already uses for document sections.

Layout-wise, follow frontend/src/pipeline/ChunkGraphView.tsx's existing precedent rather than reaching for a new dependency: a deterministic layout with no physics simulation, so the same expert always draws the same picture (a fixed radial placement — sections evenly spaced around the expert, each section's cited chunks arranged near it — computed the same way the chunk scatter's PCA-to-viewBox affine map is today, just polar instead of cartesian). One more admin-surface view alongside the existing chunk-space and knowledge-graph ones, not a new visualization stack.

Variants to test — how an expert actually answers

Four ways to answer from an expert, each a real RAG-technique tradeoff, each cheap to add as one more setup-like config to the existing eval harness rather than a new engine:

A · Scoped retrievalbaseline

Today's rag_llm, retrieval narrowed to the expert's channel/video set. No distillation at all — the expert is a scope, not a compiled artifact.

new code: nonecost: same as today
B · Community-summary expert

Answer from the cluster's existing Leiden community summaries (the global GraphRAG route, scoped to the expert's communities) instead of raw chunks.

new code: rollup mapping onlycost: lower (fewer, denser tokens)
C · Distilled-card-firstflagship

The knowledge card's playbook_sections are the primary context; raw chunk retrieval only fires as a citation-grounding fallback for specific facts the card doesn't cover.

new code: the distillation jobcost: lowest per-query
D · Card-in-system-prompt

The card's principles compiled directly into the persona's system prompt — no retrieval call at all for a matched question. Fastest, but least grounded; a good "does removing retrieval hurt more than distillation helps" control.

new code: prompt assembly onlycost: near-zero retrieval latency

These compose with the existing retrieval-technique axis too — nothing stops variant A from also being measured under hybrid+rerank vs semantic, exactly like eval-ablation --sweep extended does today. Expert scope and retrieval technique are orthogonal axes in the same harness.

The expert router

The part that actually changes the product: today every question does the same live RAG. The target behavior is auto-routing with a manual override — the app looks for a matching expert first, and a persona picker stays available for when the user wants to force one (or force the general assistant). 

sequenceDiagram
  participant U as User
  participant API as POST /api/ask
  participant R as Expert router
  participant E as Expert (card + fallback retrieval)
  participant G as General corpus RAG (today's rag_llm/agent/graph)
  U->>API: question (+ optional persona override)
  alt persona explicitly selected
    API->>E: answer as that expert
  else no override — auto-route
    API->>R: classify(question)
    R-->>API: expert_id + confidence
    alt confidence >= threshold
      API->>E: answer as matched expert
    else low confidence
      API->>G: fall through — today's behavior, unchanged
    end
  end
  E-->>U: answer, cited [P#] to the card + [#] to source chunks
  G-->>U: answer, cited [#] as today

The classifier itself is not a new pattern: GRAPH_ROUTER_SYSTEM_PROMPT / graph_agent.py already does exactly this shape of call — classify one question into a small closed set of routes before answering. Swap "local/global/temporal" for the registered expert ids plus a none route, and the plumbing already exists as a template.

Failure mode to design for, not discover in production: a wrong-but-confident route is worse than a fallback to general RAG, because it answers a career question with property expertise instead of just answering less precisely. The confidence threshold is a real tuning knob, not a formality — it needs its own eval (false-route rate on the golden set), not just "does routing work when it's obviously right."

Evaluation — reusing the harness that already exists

This is the part with the least new work relative to value: the golden set already has three labelled domains that map 1:1 onto the first three experts. No new question authoring is needed to get a first measurement.

questionmetrichow (existing machinery)
Does scoping to an expert improve retrieval over whole-corpus? recall@k, NDCG, context_recall eval-ablation's deterministic IR metrics, run per-domain — the by-domain breakdown already exists in src/evals/ablation.py.
Does a distilled card answer as well as live multi-hop RAG? RAGAS composite, answer_correctness vs the same reference answers eval-matrix with variants A–D from above as new setup-like rows, scored by the same judge already wired.
What does distillation cost vs save? avg_elapsed_seconds, avg_token_estimate Already columns in the matrix comparison — the upfront distillation LLM bill vs the reduced per-query bill is a real before/after, not a new metric to invent.
Does the expert get better as its cluster grows? composite score at increasing source_video_count New: re-run distillation on held-out-then-added video subsets of one domain (e.g. career at 3, 6, 9 videos) and plot the same golden questions' scores — a genuine learning curve, the strongest evidence for the "improves over time" claim.
Does the router send questions to the right expert? routing accuracy, false-route rate New, small: label each existing golden question with its correct route (already implied by its domain field) and score the classifier against it — near-zero extra authoring.
Does recency-weighting stop a stale claim from outranking a superseded one? answer_correctness on time-sensitive questions specifically New: the golden set already has a live test case — g013 ("how did property channels' stance on the budget's tax changes evolve"), a temporal question over exactly the kind of claim that should decay. Score the card with and without recency weighting on that question and its neighbors; a real regression test, not a hypothetical.
Net new eval work is small. One dimension (scope) added to the existing setup × question matrix, one new golden-question field (route label, derivable from the domain that already exists), and one new experiment shape (score-vs-cluster-size) that's a rerun of existing tooling on subsets, not new tooling.

Risks & open questions

Small clusters

The career domain has ~6 source videos today. A distilled card built from that little material risks reading more authoritative than it is. A minimum source_video_count gate before an expert is enabled — refusing to stand up an expert that thin — should be a hard rule, not a suggestion.

Multi-domain channels

Some channels could plausibly serve two experts (a career channel that also covers freelance-rate negotiation, say). Domain-heuristic clustering assumes one channel → one expert; embedding clustering (or explicit multi-membership) needs a decision before it's a real problem, not after.

Card staleness

A card built once and never refreshed is a worse version of live RAG — it goes stale exactly when the corpus grows, which is when it should be improving. The re-distillation trigger (manual CLI at first, scheduled/threshold-based later) needs to be a real answer, not a "later." Recency weighting (above) only ranks claims correctly within a build — it doesn't substitute for actually re-running the build when new source video lands.

Faithfulness of a second-hop summary

A card is a summary of summaries in the worst case (variant D especially). Every principle and playbook section must carry citation ids back to source chunks — enforced at generation time (the prompt requires it, like the graph extraction prompt already does) and checked at eval time (a citation that doesn't resolve to a real chunk id is a build failure, not a warning).
