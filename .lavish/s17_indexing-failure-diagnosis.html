02

Where it dies, and what it leaves behind

src/rag/indexing.py · RagIndexer.index()

Indexing a video is six steps. Steps 1–4 commit to Chroma before step 5 runs. So when step 5 raises, the transcript and its chunks are already on disk — but the job is reported as a total failure. The UI says "failed"; the database says "partly succeeded". Both are telling the truth about different things.

No — the summary is not from Supadata. Supadata's only job in this pipeline is step 2: it returns the raw timed transcript segments and the video metadata (title, channel, duration). It never produces a summary. The summary at step 5 is written by DeepSeek, from text we already hold: TranscriptSummaryGenerator.summarize() joins the stored segments, sends them to ChatOpenAI(**chat_model_kwargs(settings)) — which config.py:225 points at api.deepseek.com — and parses a JSON summary back out (rag/summaries.py:45–61, wired at cli.py:2500–2504).

Two provider accounts, two different steps. Supadata is fine and has 234 credits left; DeepSeek is the one at −$0.09.

StepProviderProducesMetered asStatus today
2 fetchSupadata timed transcript segments + video metadata 1 credit / video healthy · 234 left
5 summarizeDeepSeek a JSON summary generated from the stored transcript tokens out of balance
6 graphDeepSeek entities & claims, one call per chunk tokens out of balance

This is why in-place repair is free. Because step 5 reads the transcript we already stored at step 2, re-generating the 14 missing summaries needs zero Supadata credits — only DeepSeek tokens. That settles question 2 in §10 fairly decisively.

The retry trap. Because the transcript is already stored, re-running the same URL after a failure is not free: indexer.index() is called with refresh=True from the queue path, so it re-fetches from Supadata and spends another credit — then fails at the same step again. Four failed retries in your screenshot cost four credits and produced nothing.

05

The design: index steps 1–4, defer 5–6

your call — adopted refined by §06

Your proposal: "only do steps 1–4 in index and flag summarise / graph have not been done." That is a better fix than the one I first suggested, and it is worth being precise about why. Catching the exception (my §04 note) makes failure survivable. Splitting the pipeline makes failure structurally impossible at that point — because the LLM is no longer in the indexing path at all.

What this buys

Indexing stops depending on a paid API

Core index touches Supadata once and then only local CPU. A DeepSeek outage, a rate limit, a bad API key — none of them can fail an index again. Today's incident becomes structurally impossible.

Indexing gets much faster

The summary call is the slowest step in a job — a whole transcript in, JSON out. Removing it from the hot path shortens every index, before any concurrency work.

"Pending" replaces "corrupt"

The 14 videos stop being damage and become a work queue. Same rows, same data — but an expected state with a defined transition, not an accident nothing recorded.

Enrichment can be batched and cost-controlled

One pass over N videos, run when you choose, with its own concurrency and its own budget ceiling. You decide when to spend DeepSeek tokens rather than paying per paste.

Concurrency gets simpler

Core jobs are short and uniform — fetch, chunk, embed. Far easier to parallelize predictably than jobs whose duration is dominated by a variable LLM call (§06).

Failures stop costing credits

Defect 3 disappears. There is nothing to retry through the fetch path, so no retry re-spends a Supadata credit.

What already exists, and what's missing

Half of this is already built — the graph half. Checking before proposing:

PieceSummarize (step 5)Graph (step 6)
Runs outside the index today? no — inline, and fatal yes — queue hook, already non-fatal
Corpus-wide backfill command missing — no index-summaries. --refresh-summary exists but rides the bulk-index fetch path. exists — index-graph (cli.py:318)
Resumable / cached across runs partly — ensure_summary returns hit for an existing summary, so a re-run skips done work yes — extraction cached by chunk hash
Explicit pending state on the video missing for both — RawTranscriptDocument (rag/models.py:15–40) has summary, summary_model, summary_generated_at … but no status field. Pending is inferred from summary is None, which cannot distinguish never attempted from attempted and failed.

So the work is narrower than it sounds. Move the summary call out of RagIndexer.index(); add an index-summaries backfill mirroring the index-graph command that already exists; add one explicit state field so "pending" is recorded rather than inferred. The graph side largely just gets promoted from an implicit queue hook to the same first-class treatment.

The one real tradeoff

A freshly indexed video is invisible to summary-level routing until enrichment runs. Chunk retrieval finds it immediately, but the summary filter and GraphRAG do not — so a question routed by summary can miss a video you just added. Today that gap exists too and is silent; the difference is that it becomes expected and visible.

§06 largely removes this. If the summary is the YouTube description it arrives with the metadata at step 2, so a new video is summary-routable immediately and only GraphRAG lags. The residual question — when the graph pass runs — is question 4 in §11.

Supadata Extract is not a viable "Supadata-only" route. It is still an LLM — just theirs rather than DeepSeek's — and it is metered per minute of video: 5 credits per minute with a 5-credit floor. Your corpus is 4,463 minutes. Summarizing just the 14 pending videos would cost roughly 1,689 credits against a balance of 234, and 19 videos exceed its 55-minute hard cap outright. The known caveat, recorded rather than debated. A description is what the creator wrote to make you click; an LLM summary is derived from what was actually said. Expect descriptions to route topic well and specific claims less well, and to carry sponsor and CTA noise into the embedding. The eval ablation will put a number on that so it is known rather than assumed.

The consequence that needs a decision

110 of your videos currently have DeepSeek summaries; 14 have none. Switching the source affects new videos only unless you also rewrite the existing ones — and a corpus where 110 summaries are LLM prose and 14 are marketing copy is worse for routing than either kind alone. The summary embeddings all share one vector space, so mixing two very different registers makes similarity scores mean different things for different videos.

Rewriting all 124 from stored descriptions is free and instant — no Supadata calls, no DeepSeek, just re-embedding text already on disk (local CPU). The alternative is keeping the 110 as-is and accepting a mixed corpus. That is question 2 in §11.

What this does to the §05 design

§05 as written 4 core + 2 deferred

  • Core: discover → fetch → chunk → embed
  • Deferred: summarize (DeepSeek), graph (DeepSeek)
  • Needs an index-summaries backfill
  • New videos unroutable by summary until enrichment runs

with descriptions 4 core + 1 deferred

  • Core: discover → fetch (+description) → chunk → embed (+summary embedding)
  • Deferred: graph only
  • No index-summaries backfill needed — plan step 3 drops out
  • New videos are summary-routable immediately — the §05 tradeoff mostly disappears
  • Embedding the summary is local CPU, so the core index stays entirely LLM-free

This is a simpler system than either of us proposed. Indexing makes exactly one paid call (Supadata, 1 credit) and is otherwise local. The only deferred, LLM-dependent step left is the knowledge graph — which is already non-fatal and already has its backfill command. The 14 "pending" videos would be fixed by a re-index that costs 14 credits, or free if the stored descriptions are used directly.

07

Why there is only one worker

and what it would take to have several

You asked why indexing is a queue of one. The answer is a single guard clause, and the comment justifying it points at a limitation that no longer reflects the rest of the codebase.

The block

src/cli.py:2371

def _run_bulk_index(args, settings, ...):
    if args.concurrency != 1:
        raise ValueError(
          "bulk-index currently supports "
          "--concurrency 1 only")

The --concurrency flag exists and defaults to 1 (cli.py:726); any other value raises. Below it, the run loop is a plain for video in videos:. There is no partial implementation to finish — the parallel version was simply never written.

The stale justification

src/api/ingestion_queue.py:7–9

# a single background worker thread drains
# jobs in submission order (bulk-index only
# supports concurrency 1 anyway, so serial
# execution loses nothing)

The queue is single-worker because bulk-index is, and bulk-index is single-threaded because nobody removed the guard. It is a circular justification, not a technical constraint.

The codebase already knows how to do this

Three modules run LLM calls concurrently today, with the same ThreadPoolExecutor + ordered-results + progress-lock shape. Concurrency is not a new capability here; it just was never applied at the video level.

ModuleDefault workersWhat it parallelizesEvidence of tuning
rag/graph_extract.py:1298entity/claim extraction per chunk—
rag/contextualize.py:1388chunk contextualization per chunk—
rag/conflicts.py:16546conflict adjudication per pair—
cli.py:306–3124eval matrix cells measured "4 workers cleared 80 cells cleanly, 6–8 collapsed"

What is actually safe to parallelize

Indexing one video is ~90% network wait (Supadata fetch, then a DeepSeek summary) and ~10% local CPU (chunking, embedding). That ratio is exactly what thread-level concurrency is good at — but three shared resources need checking first.

safe Network calls

Supadata fetch and DeepSeek summary are independent per video and hold no shared state. This is the entire win. Supadata Basic allows 10 req/s, well above anything we'd send.

needs a lock Chroma writes

Both stores hold one chromadb.PersistentClient and one collection handle (storage.py:36, 133). Reads are fine; concurrent replace_chunks calls to the same collection should be serialized behind a write lock. The writes are milliseconds — serializing them costs nothing.

needs care The embedding model

HuggingFaceEmbeddingModel already guards lazy loading with a lock (embeddings.py:27) and is pinned to CPU. Parallel embedding on CPU competes for the same cores — better to keep embedding serial and parallelize only the network steps, or accept a modest slowdown per video for a large gain overall.

One shared-file race that must be handled. Every index-rag / bulk-index run ends by calling _refresh_rag_pipeline_dashboard(settings), which rewrites the single file dashboard/rag_pipeline.html. Two jobs finishing at once would interleave writes to it. The fix is small — debounce the refresh to once after the queue drains rather than once per job — but it has to be part of the same change, not an afterthought.

Two ways to get concurrency

OPTION Arecommended

N workers in the queue

Give IngestionQueue a max_workers parameter and start N worker threads instead of one. Each still runs a whole job start-to-finish.

  • Wins: parallelism across all job types — pasted URLs and channel runs alike — with no change to bulk-index at all.
  • Cost: a Chroma write lock; the dashboard debounce; per-job progress must key off the job id (it already does).
  • Risk: low. The queue is already pub-sub and each job is self-contained.
  • Suggested default: 3 — enough to hide network latency, low enough that CPU embedding does not thrash.
OPTION B

Honour --concurrency inside bulk-index

Delete the guard at cli.py:2371 and turn the candidate loop into a ThreadPoolExecutor, matching the shape in contextualize.py:161.

  • Wins: speeds up multi-video channel runs, which are the slowest thing in the app; the per-candidate try/except already isolates failures correctly.
  • Cost: same locks as A, plus keeping run.candidates in submission order under concurrent appends.
  • Limitation: does nothing for a queue of single pasted URLs — which is exactly what failed in your screenshot.

They compose. A is the broader win and the smaller change; B makes a single channel job fast. Doing A first is strictly better sequencing, because A's locks are a prerequisite for B anyway.

08

Real per-stage progress

"3/4 core steps, plus enrichment status"

You want a stepper. Two things stand between here and there — and the first is worse than a missing feature.

Problem 1 — the stages that exist are theatre

IngestionJob already carries a stage field, and _process already sets it. But look at the order of operations (ingestion_queue.py:148–165):

job.stage = "discover"   # broadcast
job.stage = "fetch"      # broadcast
job.stage = "processing" # broadcast
exit_code = self._run_blocking(...)  # ← all the work

Three stages are announced back-to-back with no work between them, then the entire index runs inside one opaque call. A stepper built on this would jump to 3/6 instantly and freeze there for the whole job. It would be a progress bar that lies.

Problem 2 — the frontend ignores it anyway

JobRow (IndexPanel.tsx:24–43) renders the status badge, the target URL, and free-text job.message. It never reads job.stage. The type is even loose — stage: string | null (types.ts:1284) — while a precise stage union already exists two lines above it for the old streaming endpoint:

export interface IndexStage {
  stage: "discover" | "fetch" | "chunk"
       | "embed" | "summarize";
  message: string;
}

Five of the six stages are already named. Only graph is missing — and under §05 it is no longer a stage at all, so the existing five-value union is exactly right: the first four become the progress bar and summarize moves to the enrichment line.

The proposed shape

Thread an on_stage callback through RagIndexer.index() so each stage fires when it actually starts — the same on_progress: Callable[[str], None] | None pattern contextualize.py:137 already uses. The queue forwards each callback to _broadcast_job, and JobRow renders the stepper below the target URL. Two new fields on the wire: stage_index for the core 4, and an enrichment object carrying summary and graph status per video.

10

Risks & open questions

A pending backlog can quietly grow forever

Once enrichment is optional, nothing forces it to run. A corpus can drift into mostly unenriched while every job reads Done — routing degrades with no red flag anywhere. Mitigation: the corpus health strip already counts missing summaries and it caught this incident; keep it prominent, and escalate its level once the pending count crosses a threshold.

Concurrency multiplies spend rate, not spend

Three workers burn Supadata credits and DeepSeek tokens three times faster. With 234 Supadata credits until the 11 Sep reset, a runaway concurrent channel run is a bigger accident than a serial one. Worth a per-run credit ceiling.

CPU embedding is the real ceiling

Embeddings are pinned to CPU deliberately — MPS wedges the server. Three concurrent jobs embedding at once will contend. The measured precedent (4 workers good, 6–8 collapse) suggests starting at 3 and measuring, not guessing.

resolved How the 14 get repaired

Settled by §05. They are not repaired — they are enriched, by the same backfill pass that will handle every future video. Zero Supadata credits, because the pass reads transcripts already stored. No separate repair path is needed.

Open — is the zero-chunk cause really an empty transcript?

Stated as "likely" above because I have not fetched those two videos to confirm. A 10-second check settles it, but it changes the fix in step 7.

Not investigated

Whether the 402 also degraded any already-indexed video's stored summary, and whether the ingestion run records under chroma/ingestion_runs captured these failures. Both are cheap to check if you want them in scope.
