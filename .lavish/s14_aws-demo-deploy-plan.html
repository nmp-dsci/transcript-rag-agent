Ship the RAG walkthrough to AWS — demo-only prod, full-power dev

Put the finished V0–V8 build in front of people: a public URL where anyone can browse the RAG pipeline, the scored results, and the existing Q&A — with no LLM calls, no ingestion, no login — while your local/dev environment keeps every capability. Analytics tell you who landed, what they explored, and whether they came back. CI/CD mirrors the data-qa-agent pattern you already run: GitHub Actions → OIDC → Terraform → build → deploy → smoke test.

One container, one service, no database, no VPC wiring, no Secrets Manager entries — the demo has no secrets to hold. This is deliberately a fraction of data-qa-agent's footprint (no Aurora, no ECS jobs, no separate frontend bucket: FastAPI already serves frontend/dist).

Decision 1 — how prod is hosted decided: A

Decided: Option A — App Runner container, demo-gated. Option B stays on record below as a later cost optimisation.

A · App Runner container, demo-gated

recommended

Ship the same FastAPI app with YT_AGENT_DEMO_MODE=1. The real API answers every read route from the baked-in Chroma + artifacts; a middleware refuses everything else. Frontend reads the demo flag from /api/health and renders the demo chrome.

  • Build cost: small — one env flag, one middleware, frontend demo chrome. No new render paths.
  • Run cost: ≈ $5–9/mo (0.5 GB provisioned ≈ $2.6/mo idle + vCPU when active + ECR storage).
  • Fidelity: the demo is the app — graphs, themes, drill-downs all live.

B · Fully static snapshot on S3 + CloudFront

cheaper, more work

An export script crawls every GET endpoint into JSON files; S3 serves them at the same /api/* paths behind CloudFront.

  • Build cost: larger — an exporter to maintain, SSE/streaming paths need shims, any endpoint with query params needs enumeration.
  • Run cost: near $0/mo.
  • Risk: every new view needs exporter work — it will drift from the app.

Good future cost-optimisation once the demo stabilises; not the first move.

The demo gate — deny by default

One switch, enforced server-side; the frontend only mirrors it. Nothing in prod depends on the UI hiding a button.

Backend — YT_AGENT_DEMO_MODE

  • Method gate: middleware returns 403 {"detail":"demo"} for every non-GET request. That kills /api/ask, /api/judge, /api/index*, /api/eval/matrix, /api/rank, /api/chunk-graph recompute, pack mutation — the complete write/LLM surface.
  • GET blocklist: the two GETs that do work rather than read are also refused: /api/eval/matrix/stream and /api/index/queue/stream.
  • No secrets in the environment at all — even a gate bug can't call DeepSeek or Supadata with keys that don't exist. The SSRF-sensitive document fetch (V1) is off with the rest of the POST surface.
  • /api/health gains "mode": "demo" — the frontend's single source of truth, and the smoke test's assertion.

Frontend — demo chrome

  • Tabs in prod: Chat · RAG Pipeline · Scoreboard · Experiments (read-only); System Design hidden.
  • Chat: composer replaced by a banner — “Demo replay — these are real judged conversations; asking new questions is disabled.” History rail, traces, citations, scores all work as-is.
  • Run/refresh/index buttons hidden; anything that would POST renders as a demo chip instead.
  • Landing: default to a curated conversation open in Chat, so the first paint shows the product, not an empty box.
Dev stays whole: the flag defaults off. Local serve, evals, ingestion, and the full Experiments tab are untouched — dev and prod run the same commit, differing only in environment.

Decision 2 — analytics decided: PostHog Cloud

Decided: PostHog Cloud, free tier — prod-only capture, cookieless, hash-route pageviews, retention cohorts from the built-in dashboard.
Constraint the app imposes: tabs are hash routes (#chat, #pipeline, #board) — server logs see one URL for the whole visit, so CloudFront-log analytics can't answer “which pages did they visit.” Pageview capture must be client-side, listening to hashchange.
OptionLanding / pages / retentionSetupCostVerdict
PostHog CloudAll three built in — retention & funnel charts, anonymous visitor IDs, no login needed Snippet in index.html + ~10-line hash-route pageview hook; cookieless mode avoids consent-banner work Free ≤ 1M events/morecommended
Umami CloudLanding + pages yes; retention is weaker (returning-visitor % rather than cohort curves) Snippet + manual hash trackingFree ≤ 100k events/molighter, fewer answers
CloudFront logs + AthenaLanding only — hash routes invisible; retention needs hand-rolled SQL over IPs Terraform + Athena tables~$1/mocan't answer the question

Wire-up either way: capture $pageview on load + every hashchange with the tab name as the path, and let the provider's dashboard do sessions/retention. No custom backend, no PII, no login.

Does PostHog work for both dev and prod? Yes. The snippet reads the mode from /api/health and the same code path serves both — the only question is what dev should send. Default in this plan: prod-only (init when mode === "demo"), so your own dev browsing never pollutes visitor/retention numbers. If you also want dev telemetry, the standard pattern is one PostHog project per environment (a second free API key, env-injected at build), keeping the two datasets separate. Recommendation: start prod-only; add a dev project later only if you find yourself wanting it — it's a one-line env change, not a re-architecture.

  2. ci.yml (exists): lint · mypy · pytest · frontend type/test/build · eval-regression gate — unchanged, still the merge gate.
  3. deploy-aws.yml (new, on push to main): assume OIDC role → docker build the demo image — multi-stage: npm run build, then a slim Python layer with src/, frontend/dist, committed artifacts, and the Chroma snapshot copied in at build time (versioned with the code, ~150 MB layer) → push to ECR → terraform apply → wait for App Runner deploy.
  4. Smoke test the live URL: /api/health says mode: demo; /api/corpus returns 92 videos; a POST /api/ask gets 403; the React shell serves. A red smoke fails the workflow.
  5. Rollback: re-run the workflow from the previous commit (image is rebuilt from that commit's code + data — fully deterministic), or App Runner's previous-image redeploy.
Why bake Chroma into the image instead of S3-at-boot: the index is part of what a commit demonstrates — the corpus fingerprint on the Scoreboard must match the data the API serves. One artifact, one version, no boot-time sync to fail, cold starts stay fast. At 148 MB it's well inside sensible image size; revisit only if the corpus grows several-fold.

Risks & open edges

Gate coverage is the security boundary. No login means the 403 middleware and the absent keys are the whole story. Mitigation is layered: deny-by-default on method (not a hand-kept route list), no secrets in the environment, and a smoke test that probes the gate on every deploy.
Torch/sentence-transformers in the image. The demo never embeds, but imports may pull heavy deps into the image (and RAM at boot). D1 checks the image runs in 0.5 GB; if it doesn't, lazy-import the embedding path in demo mode or bump to 1 GB (+$2.6/mo) — decide on evidence, not up front.
Scraping/abuse of a keyless public API. Read-only data is already public in the repo, so exposure is low; App Runner gives basic request throttling (max_concurrency), and the budget alarm catches runaway traffic cost.
Analytics + privacy. Cookieless/anonymous mode keeps the demo out of consent-banner territory in most jurisdictions; retention then relies on the provider's anonymous-visitor heuristics — good enough for a portfolio signal, not audit-grade.

Not in scope (explicitly)

  • No custom domain / CloudFront (one Terraform resource later if wanted).
  • No prod ingestion, eval runs, or admin surface — dev is where the corpus grows; shipping new data = merging a commit with an updated Chroma snapshot.
  • No login/user accounts — analytics are anonymous by design.
  • No Neo4j in prod — the knowledge-graph view serves from committed artifacts; anything that would need a live graph DB stays dev-only.
