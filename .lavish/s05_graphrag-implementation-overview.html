How would GraphRAG work in transcript·lab?

GraphRAG is roadmap P4 — and it is the project's original goal, "trend tracking across related videos." It answers the corpus-global, thematic and temporal questions that vector search structurally cannot, by building an entity + claim graph over the transcripts rather than just retrieving similar chunks. This is an overview of how that maps onto the modules you already have, grounded in the current codebase on main.

What is GraphRAG, concretely? An LLM-extracted knowledge graph you retrieve over, not just a similarity graph you draw. Entities and claims are extracted from every chunk into a graph; communities of related entities get LLM summaries. Global questions are answered by map-reducing those summaries; local ones by an entity-anchored subgraph + your existing vector RAG. MICROSOFT-STYLE ENTITY/CLAIM GRAPH
Why does this corpus want it? A channel of dated videos is the ideal temporal-graph case. Every chunk already carries upload_date, channel_id and timestamps. Stamp each extracted claim with them and you get trend timelines per entity — "how did this channel's view on rate cuts change over six months?" No competitor portfolio has that demo. BEST-FIT DIFFERENTIATOR
What does it cost? LLM extraction per chunk is the real bill — controllable. Measured against this corpus (§02): a full backfill — extraction plus community summaries — is ≈6¢ and ~300 calls. So Full GraphRAG is the decision (§09). And you still route: local factual questions go to cheaper, better vector RAG. Graph only where graph wins. ≈6¢ FULL BUILD FULL · DECIDED

01

The gap: what vector RAG can't do

Your P0/P1 stack is strong at local questions — retrieve the top-k chunks that best match a query and ground an answer in them. It is structurally blind to global questions, where the answer is spread across the whole corpus and lives in no single chunk. GraphRAG closes exactly that gap.

Vector RAG TODAY (P0/P1)

  • WINS "What did the CGT video say about the 30 June 2027 date?" — one chunk holds the answer.
  • HOW embed → hybrid BM25+dense → rerank → answer over top-k. src/rag, src/agents.
  • FAILS "What themes recur across this channel?" — no chunk contains "the themes"; top-k just returns k arbitrary mentions.
  • FAILS "How did the view on rate cuts evolve?" — needs claims ordered over time, which similarity ignores.

GraphRAG P4

  • WINS Global/thematic questions — map-reduce over community summaries built from the whole corpus.
  • WINS Temporal questions — claims carry upload_date, so an entity's stance becomes a timeline.
  • HOW extract entities+claims → graph → communities+summaries → route query to local subgraph or global map-reduce.
  • COST pays an up-front LLM extraction bill; ties vector RAG on local questions, so you route, not replace.
Important: the chunk graph you have now is not GraphRAG.

src/rag/graph.py is a "k-nearest-neighbour similarity graph over transcript chunk embeddings" (its own docstring) that the frontend ChunkGraphView draws. It is exact cosine similarity for inspection — it has no entities, no claims, and never participates in answering. GraphRAG builds a semantic entity/claim graph and retrieves over it. P4 upgrades the viz into a real retrieval surface; it does not reuse the similarity edges.

Full GraphRAG vs LazyGraphRAG — the cost lever.

Microsoft's original GraphRAG summarizes every community up-front (thorough, expensive). LazyGraphRAG builds only the graph at index time and defers summarization to the moment a global question is asked, reportedly matching quality at a fraction of indexing cost. That lever matters at enterprise scale — but the backfill math below prices this corpus's full build at ≈6¢, so the review decision (§09) is Full: summarize up-front, revisit Lazy only if the corpus grows ~100×.

Backfill math — calls & dollars for this corpus, today

Measured from the live Chroma store (.yt-agent/chroma): 10 videos → 281 chunks, 326k chars of chunk text ≈ ~82k tokens (~290 tok/chunk). Priced at deepseek-v4-flash — the configured default in src/config.py — at $0.14/M input (miss) · $0.0028/M input (cache hit) · $0.28/M output. The shared extraction prompt rides DeepSeek's automatic prefix cache, so only chunk text pays the miss rate.

04

The data model

Three record types. The claim is the load-bearing one: it is what an answer cites, and it carries the source chunk id and upload_date that make both grounding and the temporal layer work. It fits your existing pydantic + chunk-id conventions (chunk:<video_id>:<index>).

the three graph records (shape sketch)
# entity — a canonical thing the corpus talks about
Entity(id="cgt-discount", name="50% CGT discount", type="policy",
       aliases=["capital gains discount"], mentions=37)

# relation — a typed edge between two entities
Relation(source="cgt-discount", target="june-2027",
         type="phased_out_by", weight=0.8)

# claim — the load-bearing record: cited, dated, entity-linked
Claim(text="The 50% CGT discount phases out on 30 June 2027.",
      entities=["cgt-discount", "june-2027"],
      source_chunk_id="chunk:7m27Go3K1d0:3",   # grounds the citation
      video_id="7m27Go3K1d0",
      upload_date="2026-05-14",               # the temporal key — already on the chunk
      polarity="asserts")

# community — a cluster of related entities + its LLM summary (lazy = null until asked)
Community(id=4, entities=["cgt-discount", "negative-gearing", ...],
          summary="This channel frames the budget as...")

Because a claim points back at a real source_chunk_id, graph answers keep the same timestamped, deep-linkable citations your vector answers already produce (src/rag/references.py) — no new citation story to invent.

05

The distinctive payoff: temporal trend tracking

This is the original project vision and the demo nobody else's portfolio has. Because every claim inherits upload_date from its chunk, an entity's claims become a timeline — and "did the view change?" becomes answerable with evidence instead of vibes.

EX

Worked example — "How did this channel's stance on rate cuts evolve?"

  • 1. Resolve the entity rate-cuts in the graph.
  • 2. Gather every claim linked to it, each with its upload_date and source_chunk_id.
  • 3. Order by date and detect the shift: e.g. Mar "cuts unlikely this year" → May "one cut priced in" → Jul "expects two cuts."
  • 4. Synthesize a dated narrative, each step deep-linked to the exact video moment.
Evidence produced: a trend timeline in the workbench (upgraded ChunkGraphView) and a narrated, citation-backed answer — the kind of "reasoning over a corpus's evolution" that reads as senior.

The deliverable is a comparison matrix: every engine answers the same golden questions, every answer is scored the same way (RAGAS + IR metrics), and the run is committed so "GraphRAG wins global questions" is a number in evals/runs/, not a demo. Judge runs are deliberate, one-off, and committed — CI never waits on RAGAS.

The RAGAS judge is slow and stalls on long answers (known from P1), so the matrix runs in two modes: the full judged pass is an explicit offline run (--judge, ~75 answers at 5 engines × ~15 questions — cheap in dollars, slow in wall-clock; cap answer length for judging) whose scored output is committed once; day-to-day CI and re-runs replay committed runs --no-judge, exactly the discipline the repo already follows.

Also eval the extraction itself.

GraphRAG has a failure mode vector RAG doesn't: bad entity/claim extraction silently corrupts every graph answer. Add a small extraction-quality check (precision/recall of extracted claims against a hand-labelled sample) so a graph regression is visible, the same way context_recall makes a retrieval regression visible. Faithfulness-over-claims (above) is the runtime symptom; this is the root-cause check.

Decisions taken in review (26 Jul 2026) — all four are now folded into the sections above:

1 · Where does the graph live? DECIDED · NEO4J

Storage backend for entities/relations/claims.

Neo4j — chosen: named in the JD corpus (Culture Amp), and Cypher + graph-modelling experience is itself the portfolio signal. Run as a docker-compose service (community image) + the official Python driver; the graph stays derived and rebuildable, so the heavier dependency is low-risk.
networkx in-memory — demoted: fine for a spike, but produces no JD-visible experience.
Postgres (P2 pgvector) — not needed for the graph; P2 still owns vectors later. Bonus: Neo4j fully decouples P4 from P2.

2 · Full or Lazy GraphRAG? DECIDED · FULL

When to pay for community summaries.

Full GraphRAG — chosen: the §02 backfill math prices the entire full build at ≈6¢ today, ≈60¢ at a 100-video corpus — comfortably under $3 with any slack. Pre-summarized communities make global answers fast and demoable.
LazyGraphRAG — revisit only if the corpus grows ~100× or re-index churn gets high; chunk-hash caching already blunts re-index cost.

3 · Sequence vs P2/P3 DECIDED · START P4 NOW

Time difference: s04 sizes P2 at ~2–3 wk and P3 at ~2 wk — waiting costs ~4–5 weeks of evenings before any graph work starts.

Start P4 now — chosen: graph demo lands ~4–5 weeks sooner, and with Neo4j the early start has ~zero rework — the graph store never migrates to Postgres.
P2 → P3 → P4 — the original spine; its one advantage (a single shared store) is removed by the Neo4j decision.

4 · Scope DECIDED · WHOLE CORPUS, QUERY-TIME FILTER

Where the graph is built vs where a question looks.

Whole corpus, scoped per question at query time — chosen: index everything; each question picks its own slice in the background — the router classifies intent, entity resolution anchors the subgraph, timelines filter by entity + date. Same philosophy as the existing summary-filter (query-time video filtering for vector RAG); no assumptions baked into the index.
Property-domain pre-filter — rejected: pre-filtering hardcodes today's question mix into the index.
