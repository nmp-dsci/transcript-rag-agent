A front end is not a taste argument. It is a scored one.

Twelve dimensions, each with a written Low / Medium / High descriptor, drawn from twenty talks by working designers, design-system leads, front-end system-design interviewers and AI-build practitioners. Use it to grade an app you already own, then to specify the version that grades higher. The answer: score the surface, but fix the system

Yes — front-end quality is rubric-able, and this guide is the rubric. But the scoring only works if you separate two things the corpus keeps separating. What a reviewer sees is colour, hierarchy, type, spacing, motion. What is actually wrong is almost always one layer down: a token that was never given a role, a component that was never given a state, an accent colour that was never given a budget. Score the surface. Then write the remediation against the system, because with a real design system one fix propagates, and without one you get a dashboard button and a chat button with different corner radii in the same product inside the same app.

The corpus is unusually consistent about what separates junior work from senior work, and it is not decoration. It is restraint: one accent colour with a job, one primary action per screen, one content focal point, and a spacing system that is arithmetic rather than opinion. The top-tier login screen in the corpus wins on colour, hierarchy, spacing, layout and imagery — five nouns, no novelty. The senior dashboard wins by removing things, having stripped away a lot of the brand colour so the data can speak.

“The old adage is that if everything is on fire then nothing is on fire, and the firefighter doesn't know which area to address.” Jesse Showalter, Amateur vs Pro UI Design

Score cold, twelve times

Run all twelve dimensions before proposing anything. Low = 0, Medium = 1, High = 2, out of 24. The corpus's own self-audit habit is to score out of 100 with a deliberately strict prompt, treat 67/100 as a real first build, and treat anything above 80 as launch-ready. That maps to 19/24 here.

Name the tier tell

Every Low has a signature. Heavy drop shadows everywhere are not a style choice; they are what happens when someone can't create separation with contrast. Name the tell, not the vibe.

Propose at token level

A remediation that says “make the buttons nicer” is unscoreable. One that says “introduce border-focus at 2px, retire the three component-specific greys” is. Tokens exist precisely so that nobody hunts hex codes by hand.

The twelve-dimension scorecard

Score each dimension Low (0), Medium (1) or High (2). The dimensions are equally weighted — that is an editorial call, not a corpus claim; no source in this corpus weights design dimensions against each other. Total 0–24 · <10 rebuild · 10–18 remediate · 19+ ship

Read the Low column as a detector, not an insult. Most of these failures are one variable away from their High.

3 · Typography

Is the type scale generated, or guessed?

Low (0)Medium (1)High (2)
Four or more font families; sizes chosen per component; body copy below 16px. Base paragraph size should always be 16, because at 14 legibility becomes font-and-weight dependent. Two families with intentional contrast — cap the site at two, three at the absolute max — and named heading styles that decrease at each increment, but the increments are eyeballed. Scale generated from a ratio — a major third (1.25) or an augmented fourth at 1.414 — with line-height at 1.2× the size and every value rounded to the nearest multiple of four. Roles are assigned deliberately: the face with greatest small-size readability carries body, buttons, menus and captions readability drives the pairing; a serif headline is a luxury signal, not a default serif reads premium.

4 · Spacing and alignment

Is whitespace arithmetic, or vibes?

Low (0)Medium (1)High (2)
Arbitrary pixel values; ambiguous proximity, where a logo lockup looks half-attached to its heading and grouping reads accidental put it in an auto layout. An eight-point system is applied to components — every dimension a multiple of eight, e.g. a button at 16px vertical, 32px horizontal — but section rhythm is inconsistent. Component spacing and section rhythm both come from the scale, and the rhythm is deliberately re-scaled per breakpoint rather than inherited: 256px between major sections on large screens, stepping down to 168 on tablet and 96 on phone. A formal grid system is optional and can add unnecessary complexity grids are optional.

6 · Components and states

Low (0)Medium (1)High (2)

Complex components decompose into atoms: a table has cell and heading atoms, not one rigid table baked around today's columns atomic sub-components. The rule for promotion is blunt — used more than once, it's a component.

7 · Responsive and touch

Low (0)Medium (1)High (2)

Breakpoints exist — e.g. laptop above 1200px, tablet 1200–600, phone under 600px — and type scale shifts with them, but spacing and component behaviour are hand-patched per screen. A single system with per-breakpoint layout variables, so one semantic value like page margin resolves differently on desktop and mobile without duplicating tokens breakpoint-scoped padding and gap; you do not maintain a completely different mobile design system, only mobile-optimised variants on the components that genuinely change. 8 · Accessibility

Text hits roughly 4.5:1 for small text, 3:1 for large, checked in DevTools, and every palette tint was contrast-checked before the palette was locked checked against its background. All of Medium, plus graphical elements such as inactive nav icons clearing the 3:1 minimum for graphical elements via controlled opacity rather than eyeballed washes; a visible focus state tied to a token focus token; and an explicit reading order in handoff, because the designer's default left-to-right-then-down is not always the logical order. Run an automated accessibility review as a gate — one such pass on a single frame surfaced 22 issues: 3 critical, 13 major, 6 minor.

9 · Motion and feedback

Does motion carry information, or is it decoration applied everywhere?

Low (0)Medium (1)High (2)
Either no motion at all, or wall-to-wall animation and scroll effects, which makes a site playful and visually exhausting. Long waits shown as a bare spinner. A signature treatment — a liquid-metal border, a shader — smeared across the whole UI instead of reserved for a few unique moments. Hover and tap feedback exist on primary controls; transitions are present but unmodulated across the page. Motion has rhythm: high-motion sections alternate with calm static ones, and purposeful motion is what turns a layout into an experience. State changes are legible — an active tab gets at least two simultaneous visual changes, plus a sliding underline between tabs. Waiting is narrated, not spun: a per-phase text label with a gradient wipe rather than dots, or intentional loaders that make dead time feel deliberate. Stylised shadows are allowed when they are thick, bold and on purpose and confined to elements that deserve attention.

Some measurement — First Contentful Paint and Time to Interactive tracked in DevTools before optimising measure first — plus compressed WebP assets that take a multi-megabyte image down to about 100KB WebP. Goals stated as Core Web Vitals plus real-user monitoring and broken into the three named dimensions — loading speed, input responsiveness, layout stability. A deliberate rendering strategy chosen from the five available. Re-render discipline via memoised components React.memo, lazy loading so heavy charts load on demand, caching by read/write ratio read/write ratio, and search inputs debounced by 500ms. Visual richness is not an excuse for weight: a fully 3D landing page in the corpus shipped at under 1MB.

All of Medium, plus imagery that looks shot by one photographer in one session, a hero carrying a real image or video because text-only heroes look plain, and instrumented outcomes: analytics key events fired on purchase or form fill so a redesign can be proven rather than argued.

Moving the surface dimensions up a tier

Dimensions 1–4 are where a reviewer forms their verdict in the first second. Each one has a small number of levers that reliably move a Low to a High.

Colour

  • Give the accent a budget before you pick it. It is for primary calls to action and primary areas of concern nothing else.
  • Start from three core colours — primary, secondary, background — before any accent exists three main colours, and store each as a variable, not a filled shape as a variable.
  • Allocate roughly 60% neutral, 30% brand, 10% accent 60-30-10.
  • Build tints, shades and tones deliberately — white, black and grey mixed into the base tint, shade, tone — and work in RGB/HSB for screens, with hex as the exchange format hex for the web.
  • In practice, only three harmonies get used: analogous, monochromatic, complementary the three that matter. Blue is the internet's most-used colour because it reads as trust most used — which is an argument for choosing it deliberately, not by default.
  • Internal and enterprise tools earn a restricted palette. One team deliberately shipped black, white and grey because simplicity read as more proper for the use case black and white on purpose.

Hierarchy

  • One primary action per screen. A second equally weighted CTA is the single most common junior tell demote it to a link.
  • Differentiate every text role: label, placeholder, body, link. Uppercase, opacity, underline — pick a treatment, but pick one links must look like links.
  • In dense tools, cut the chrome. Shrink the top bar and sidebar until the charts, not the logo, are the focal point content first. Once the user is inside the product, it's not a branding moment anymore.
  • Place controls by scope: global search in the global nav, section filters in the section, so users can predict what a control will affect scope reads from position.
  • Choose the right disclosure pattern: tabs show exactly one panel; accordions can show several and suit simple text, which is why FAQs use them tabs vs accordions.

Type

  • Anchor the scale at a 16px base, then generate upward with a ratio and 1.2× line-height, rounding to multiples of four no unnatural jumps.
  • If you need airier display type, raise the base deliberately — one worked example uses a 21px base 21px base with an augmented fourth ratio.
  • Every size becomes a named style, never a one-off. Build H1 through H5 as reusable styles so a change is one edit named styles, starting around 36px for H1.
  • Pair by contrast and by role. Brandon Grotesque over Proxima Nova works because Proxima stays legible at 16–18px where the display face does not a worked pairing.
  • Source from Google Fonts or Adobe Fonts; the paid library buys you filtering by weight, width and x-height two sources.

Space

  • Adopt eight-point spacing and apply it to margins, padding, widths and heights alike — the payoff is consistency and an easier developer handoff multiples of eight.
  • Fix grouping with layout, not nudging. Putting a lockup inside an auto layout with consistent spacing makes the grouping read as intentional auto layout; auto layout behaves like flexbox like flex, and text blocks set to hug their container re-space themselves as copy changes hug contents.
  • Re-scale section rhythm per breakpoint rather than letting desktop whitespace ride down to the phone: 256 → 168 → 96 stepped rhythm.
  • A formal grid is optional; rulers and guides are often enough and are easier to keep honest optional complexity.

The system underneath the score

Dimensions 5 and 6 are where remediation should be written, because they are the only place a fix becomes permanent. A design system is a single source of truth for all things design: components, guidelines and brand identity in one place. A token is not a hex code — it is a hex code that has been given a role and assigned to components.

Build the token layer

  • Pick an architecture and stick to it: two-tier primitive/semantic, or three-tier brand/alias/mapped when many brand scales must coexist two or three tiers.
  • Derive colour scales by blending the base against white and black at 80/60/40/20/10% so the numeric names (100, 200, 950) are earned by the step size rather than guessed scale maths.
  • Keep the small token families genuinely small. You rarely need more than three or four border widths or radii none/small/medium/large.
  • Write the usage description for every variable. Without it neither a human nor an agent can tell a default surface from a secondary one — the description is the most important part.
  • Never let one component own a token always bad. The whole return on tokens is that a brand change propagates and nobody search-and-replaces hex codes.

Build the component layer

  • Componentise on the second use used twice, componentise — but don't push single-use flow elements into the shared library.
  • Design the state set before the styling: default, hover, active, disabled, plus a subdued secondary every state.
  • Merge near-duplicates into one component with switchable variants rather than shipping a component per variant combine as variations.
  • Decompose complex components into atoms — cell atoms, heading atoms — so a table isn't welded to one column set atoms, not monoliths.
  • For mobile, add a mobile-optimised variant to the components that actually change; don't fork the system one system.
  • Name every layer and group as you create it. Waiting leaves you with dozens of indistinguishable groups name immediately.

Keep it in sync

  • If the dev side adopts a framework like Radix, rename every Figma variant and property to match its documentation exactly, or the dev side suffers and you accrue technical debt from two conflicting sources of truth one-to-one or confusion.
  • Do not clone a public design system wholesale. Carbon and Polaris encode years of another organisation's debt and history — absolutely do not do that.
  • Budget for the tooling reality: publishing a Figma library requires a paid workspace paid tier, and dev mode is a separate seat you may need to negotiate temporary access to separate seat.
  • Keep design-system CSS separable from app code at the build level: it changes far less often, so it caches independently more stable than the app. CSS-in-JS injects style tags into the document and defeats that.

Two paths into the system exist in the corpus and both are legitimate. You can hand-build it: a dedicated style-guide page split into typography, colour and illustration frames on a 1440×1024 canvas, before any real page layout. Or you can seed it: download the one component whose look you want and tell the agent to create a design system based on this component, or feed a full-page screenshot with “please create a design system with the attached page”. If you have no reference at all, Vercel publishes its own design.md in light and dark as a starting base a public base. What the corpus disputes is how far the seeded version gets you — see Contested.

The non-functional half

Dimensions 7, 8 and 10 fail silently. A designer reviewing screenshots will never catch them, which is exactly why they belong in a rubric. Separate what the UI must do from how well it does it at the very start — the difference between whether a car takes you from A to B and how efficiently it does so.

Rendering and bundle

  • Choose deliberately among static generation, incremental static regeneration, server-side rendering, client-side rendering and partial pre-rendering five strategies.
  • Measure before optimising: First Contentful Paint and Time to Interactive in the DevTools performance tab FCP and TTI.
  • Stop cascade re-renders with memoised components React.memo, memoised callbacks useCallback and cached computations useMemo.
  • Lazy-load heavy analytics and chart components on demand on demand, and shrink what's left with tree shaking and bundle splitting.
  • Prefer Vite for new builds; reach for a Webpack-compatible Rust bundler only when you're speeding up an existing Webpack setup Vite by default. When a front end grows past safe deploys, split it into independently deployable micro-frontends micro-frontends loaded via Module Federation.

Data and state

  • Keep state shapes simple. When two values are always fetched and used together, merge them — simple beats complex.
  • Don't write custom fetch hooks. Plain useState for component state, a library like TanStack for fetching and caching TanStack.
  • Cache server responses in client state so repeat reads don't re-fetch fewer calls, but set an expiry, because other users mutate the same data expire it — in React Query that's staleTime.
  • Cut overfetching at the API shape: request only the fields the UI renders GraphQL, with in-memory caching on repeat queries Apollo cache.
  • Paginate with a cursor for feeds: fetch N+1 so the extra row tells you whether more exists, accepting that you lose arbitrary page jumps 11 for 10.
  • Insert a backend-for-frontend when the upstream API shape is volatile or you don't own it, so the UI depends on a stable interface — which also narrows the search space when an agent does root-cause analysis.

Live data and weight

  • Never poll from the client for live widgets. Ten graphs on one screen at a two-second interval is ten requests per client per tick — they will DDoS your back end.
  • For server-to-client-only updates, Server-Sent Events are the native fit; WebSockets are overkill unless the client also pushes SSE.
  • Decide what to cache by read/write ratio: yesterday's time-series point never changes, so cache it hard; only the newest point can't be read/write ratio.
  • Compress and convert images; the same asset drops from megabytes to around 100KB with no visible loss WebP. Rich does not mean heavy: an interactive 3D landing page in this corpus shipped under 1MB.
  • Size the deployment for the traffic. A chat-style app for around 40 concurrent users was sized at 2 vCPUs and 4GB RAM, with 1GB called out as too low.

Accessibility and handoff

  • Check contrast before the palette is locked, not after — several tints in a tonal scale will fail proper contrast against its background.
  • Targets: roughly 4.5:1 for small text, 3:1 for large text, and 3:1 for graphical elements including inactive nav icons.
  • One H1 per page, stating the page's topic — the one heading you never duplicate one H1.
  • Annotate reading order in handoff files. Free stamps exist for it the CVS Health annotation kit — but place the numbers yourself, because never forward raw AI annotations.
  • Prototype the journey before handoff by linking screens so navigation problems surface early an interactive mockup. Test mobile on a real device; a preview that looks fine on your monitor can feel wrong under a thumb safe area.

Dimension 12, in detail: what AI slop actually is

Distinctiveness is the dimension most reviewers skip and most users notice. The corpus is specific about the tell: the default output is the same purple gradients, the same Inter font, and a fully AI-designed app is visually identifiable by its smell — odd borders, generic components, no point of view. The root cause is upstream of the model: ask something too vague and you get something extremely standard.

There is also an honest cost. Getting non-slop output is not the cheap path — high-fidelity AI design costs meaningfully more in tokens, money and time it will lose a lot of tokens. In one controlled dashboard-generation test, one model returned great quality in 2 minutes and 47,000 tokens while a canvas-native tool burned 155,400 tokens on a single dashboard. Budget for it or accept the score.

Raise the floor

  • Install a design skill that forces a decision before code: pick a real aesthetic direction, require genuine typography pairing, block generic components, enforce CSS variables direction before code.
  • Hand-pick two or three skills. Installing everything from a repository burns context and confuses the agent.
  • Run design work at high reasoning effort. Extra-high is described as the bare minimum for non-slop output — though see Contested on the cost of maxing it everywhere.
  • Once a technique works, capture it as a reusable skill instead of re-prompting it turn it into skills; directories exist for finding them skill directories.

Raise the ceiling

  • Seed with real references — three to five screenshots from sites you admire, so the model infers taste instead of guessing from adjectives share screenshots.
  • Or let the agent fetch them: an inspiration MCP server can be asked to find the top UI for a mobile travel app, and then to break a visual direction down into key themes.
  • Clone, then mould. Pasting a reference URL with “recreate this in a single HTML file, self-verify until it's perfect” is a starting point, not a deliverable.
  • Generate options before committing. Five style directions from one brief, then converge by grafting across them five options, telling the tool to go deeper on one while borrowing nav and type from the others.
  • Start at the widget, not the page. Senior practice is to generate eight distinctively different versions of the single most important widget first widget generation first, then build the surrounding page yourself — and only repeat the exploration on widgets you're stuck on not every widget.
  • Build section by section, hero first, rather than generating the whole site at once build it in pieces. Brief on feeling and objective and let the model propose the how what, not how.

Know the ceiling

  • No current coding model has strong visual judgement despite vendor claims — they lack any visual intelligence — so anchor them with stable artefacts (a design system, a state diagram) and let them interpolate between checkpoints.
  • No tool one-prompts a world-class flow; viral demos hide significant manual polish no one-prompt UX.
  • AI has largely commoditised front-end code, not front-end judgement: there is a real gap between creating the front end and doing the design and UX.
  • Always inject your own taste on top of the generated base, or the product looks like everybody else's no sauce.

The review pass

Six stages. Run them in order; the order is what stops an agent from proposing a redesign before it has a diagnosis.

1

Inventory the surface

You cannot score what you haven't enumerated.

  • List every distinct screen, every colour actually used, every font family, every spacing value, every component that appears more than once.
  • Build a flow home base — one page linking every flow you want reviewed — so an agent can navigate between them and back flow home base.
  • Capture screenshots with numbered annotations; numbering produces far more precise, itemised findings than prose numbered screenshots.
2

Score cold, before any fix

Scoring and solving in the same breath produces flattery.

  • Assign Low / Medium / High to all twelve dimensions with a one-sentence justification and a screen reference each. No recommendations yet.
  • Make the rubric deliberately strict and treat the number as relative: above 50% is not bad, above 80% is launch-ready above 80 is amazing.
  • Expect the first honest score on a working product to land mid-range — the corpus's own first self-audit came back at 67/100.
3

Locate the tier tell

Every Low has a named cause in this corpus. Use the name.

  • Colour Low is almost always accent overuse everything on fire; hierarchy Low is usually two equal CTAs or undifferentiated link text no treatment difference.
  • Separator-and-shadow clutter is a contrast-skill tell, not a style the tell.
  • Cross-screen inconsistency is a missing-system tell, not a carelessness tell inconsistency.
4

Test the flows, not just the frames

Dimensions 2, 7 and 11 only fail in motion.

  • Run a think-aloud test with someone unconnected to the project: have them scroll the homepage and think out loud, then attempt one specific task while you watch for silent assumptions.
  • If no user is available, run a persona-driven agent pass: give it a role, experience level and goal, and ask it to narrate expectations, hesitations and confidence on a 1–5 scale per step, then compare two flows with reasons.
  • Treat that verdict as a lens, not a truth — never take an AI suggestion 100%.
  • Design the critical flow backwards from its destination, fixing every dead end on the way back to entry trace it backwards.
5

Write the remediation at token and component level

A proposal that can't be diffed can't be scored.

  • Ask for a gap analysis against current state and a plan built from reusable design-system components rather than one-off pieces gap analysis then plan.
  • Express every fix as a token added, retired or re-scoped, or a component variant added — so one edit propagates it affects the entire thing.
  • Give the agent the design system as context, not instructions. Once a system is attached, generated pages follow the colours, the font, the spacing without being re-told.
  • Escalate model tier as the work spans more interacting components; fast models that handled scaffolding start failing switch to a beefier model.
  • Split system work into one skill per component category — form elements, navigation, data display — rather than one skill for the library, which makes the agent bounce between components one per category.
6

Re-score, and force verification

Agents grade themselves generously unless the harness forbids it.

  • Re-run the identical rubric after each round of fixes and diff the scores; the audit is only useful as a repeated measurement.
  • Add a hook that fires before the agent is allowed to finish, forcing it to recheck the work — agents are prone to picking the easy way out in verification. Deterministic hooks that constrain bad behaviour are among the most underrated harness features control, not just tools.
  • Keep each remediation sub-task bounded to roughly 50k–150k tokens; larger subtasks drift into a high-context zone where quality degrades. Use files as the handoff surface between passes — the file system is the most foundational harness primitive.
  • Stop treating public benchmarks as evidence; build your own representative set of tasks your own bench. This rubric, applied to your own screens, is that set.
  • If you pipe a review agent's findings straight back into a coding agent, supervise it: the two can correct each other into an infinite loop.
  • Preview locally and never redeploy without explicit approval, so the live product can't drift from what was reviewed never deploy without asking.

Prompts to copy

Four prompts: score, remediate, self-audit in a loop, and user-test without users. Paste them with your screenshots attached and the design system, if one exists, in context.

Where the corpus disagrees

Three splits matter enough to change how you apply the rubric. Don't paper over them.

  • Can AI build your design system? One position: download a component you like and tell the agent to create a design system based on this component, treated as reliable. The opposing position, from the two deepest design-system sources: AI cannot do those things, because it doesn't know your brand, your components or your product; and no, it cannot — what gets called a generated design system is a few styles, some variables and maybe one button. Asking AI to build tokens is compared to hiring someone to build you a kitchen on the brief "make it dark". The measured middle: out-of-the-box design-system sync works about 28%, while per-grouping skills get you to roughly 80–85% with the last 15% manual. Rubric implication: a generated system scores Medium on dimension 5 at best until a human has assigned roles and written usage descriptions.
  • How much personality should an interface carry? One side: interfaces are tools and should be simple, easy, straightforward and sometimes a little boring, with brand stripped out. The other: hover micro-interactions, gradient and liquid-metal treatments and playful motion are what mark an exceptional, non-generic product motion takes it to the next level. Rubric implication: dimensions 9 and 12 are scored against product type. A dense internal dashboard scores High on motion by being restrained; a marketing landing page does not.
  • Is maximum reasoning effort always right? One source calls extra-high the bare minimum for design output. Another measured the opposite under a time budget: max effort throughout scored 53.9% due to timeouts against 63.6% at high. Rubric implication: max effort for the scoring and the design-direction passes; high for mechanical remediation.
  • A fourth, smaller split: whether the craft must be hand-built at all. One source teaches the whole system manually — style guide, colour variables, type styles, component variants — before anything ships manual style guide first. Another argues that being purely a front-end builder is no longer valuable because the build step is commoditised you're cooked, while conceding AI still lacks the design and UX judgement. The role the corpus converges on is design engineer.

What this rubric cannot score

Honest limits. Every item below is something a reader would reasonably expect and the corpus does not supply. If your reviewing agent tries to score these, it is inventing.

  • Accessibility beyond contrast, focus and reading order. No source in the corpus covers ARIA patterns, keyboard-navigation specifics, screen-reader testing protocol, or focus management in modals and dialogs. Dimension 8 is therefore narrower than WCAG.
  • Outcome evidence. No source ties a specific design decision — a colour, a hierarchy change, a layout — to a measured conversion rate or task-completion time. Every High in this rubric is a craft judgement, not a proven lift.
  • Dense enterprise UI. The pattern vocabulary in the corpus is marketing- and portfolio-oriented. Data tables, complex validation, bulk actions, permissions UI and empty/error states at scale are unaddressed.
  • Motion as a discipline. Easing curves, durations and a framework for when to animate never appear. The corpus offers examples and a rhythm heuristic, nothing measurable.
  • Desktop and tablet navigation patterns. The only navigation source scoped to numbers is mobile bottom nav. Sidebar, mega-menu and command-palette patterns are uncovered.
  • Design-system versioning and migration. How to version tokens across breaking changes, or keep a system in sync post-launch across releases, is never discussed.
  • Team workflows. No source covers several designers prompting against one shared system simultaneously, or handoff when designer and builder are different people — nearly every example is one person doing both roles.
  • Native mobile. iOS and Android platform guidelines and platform-specific component libraries are absent; only responsive web variants are covered.
  • Real budgets. The corpus gives relative token and time figures for AI design tools but no subscription pricing or cost-per-design, so you cannot build a budget from it alone.
  • Dark mode in practice. Tokens are said to make theming easy, but no source works through an actual dark-mode palette, contrast re-check, or elevation model.
